# 促销校验规则文档

> ⚠️ **修改联动**：本文件与 `validate.py`（同目录）强绑定。
> - 改规则 → 先更新本文件，再同步修改 `validate.py`
> - 改代码 → 先确认本文件规则，修改后同步更新本文件
> 两者不同步 = 代码行为与文档不一致 = 校验结果不可信

---

## 一、模块职责

促销校验模块（`validate.py`）负责：
1. V1 金额校验：|划线价 - (促销总金额 + 支付价)| ≤ 1.0
2. V2 促销归类校验：所有促销名称必须在码表中精确命中
3. 比价平台校验：不在[携程/美团/飞猪/同程]中 → 标记不可比价
4. 解析促销明细，匹配码表类型，写入独立促销数据文件
5. 将 case_audit 写入 state.json，供兜底模块和归因模块使用
6. 促销校验完成后，若有 V1/V2 错误，可直接运行兜底处理（`validate_fallback.py`）。默认兜底为批量脚本化处理，不依赖 ANTHROPIC_API_KEY；需要调用 Claude API/Vision 时才显式使用旧版 LLM 模式。

---

## 二、促销名称标准化规则

匹配前对促销名称做标准化处理，消除格式噪音：

| 操作 | 说明 | 示例 |
|------|------|------|
| 去除所有空格 | 含内部空格 | "五一 特惠" → "五一特惠" |
| 去除噪音符号 | `_`、`。`、`，`、`、`、`；`、`：`、`.` | "五一_特惠" → "五一特惠" |
| 去除首尾空白 | strip | " 五一特惠 " → "五一特惠" |
| **保留 `-`** | 结构性分隔符 | "酒店神券-五一特惠券" 保持不变 |

标准化后做精确匹配。未命中 → V2校验失败，写入 case_audit，最终汇总输出。

---

## 三、促销明细文本格式

原始数据中 `Q优惠明细` / `促销明细（竞品）` 为自由文本，格式为每行一条：

**Q侧（携程）格式**：
```
促销名称-¥金额
促销名称——¥金额
```

**竞品侧（同程）格式**：
```
促销名称：金额
促销名称:金额
```

解析方式：逐行用正则提取促销名称和金额，支持全角/半角冒号，无需¥符号。

## 四、V1 金额校验

**规则**：`|划线价 - (促销总金额 + 支付价)| ≤ 1.0`，Q侧和竞品侧各校验一次。

| 校验项 | 公式 | 容差 | 失败写入 case_audit |
|--------|------|------|---------------------|
| Q侧金额校验 | \|Q划线价 - (Q促销总金额 + Q支付价)\| ≤ 1.0 | ±1.0 | "真实错误:V1错误：Q金额不平衡（差值=X）" |
| 竞品金额校验 | \|竞品划线价 - (竞品促销总金额 + 竞品支付价)\| ≤ 1.0 | ±1.0 | "真实错误:V1错误：竞品金额不平衡（差值=X）" |

> 划线价或支付价缺失时，跳过该端的金额校验。

---

## 五、V2 促销匹配校验

**规则**：促销名称标准化后，所有促销必须在码表中精确命中。有一条未命中即失败。

| 校验项 | 失败条件 | 写入 case_audit |
|--------|---------|-----------------|
| Q促销匹配 | 任一Q促销名称标准化后未命中Q码表 | "真实错误:V2错误：Q促销未匹配-[名称]" |
| 竞品促销匹配 | 任一竞品促销名称标准化后未命中竞品码表 | "真实错误:V2错误：竞品促销未匹配-[名称]" |

> V1/V2 失败不阻塞流程，写入 case_audit 后归因模块会写入主数据「人工校验内容」列。

---

## 六、不可对比场景判断

**触发条件**：`客服判断场景` 字段命中以下关键词之一时，跳过 V1/V2 校验和促销分行写入。

| 关键词 | 类型 |
|--------|------|
| 民宿 / 团购 / 预售 / 已下单 | 不可比价场景 |
| 不可对比平台 / 非可对比平台 / 非可比价平台 | 平台不合规 |
| 物理房型 / 酒店缺失 / 无该酒店 / 没有该酒店 | 供给缺失 |
| 更好更贵 / 更差更贵 | 同质化缺失 |
| roomid（不区分大小写） | 无法查询 roomid |

## 七、码表文件说明

### 7.1 码表文件路径

| 码表 | 文件路径 | 说明 |
|------|---------|------|
| 携程 Q码表 | `code_tables/C_Q.xlsx` | 去哪儿侧促销码表（携程场景） |
| 携程 竞品码表 | `code_tables/C_C.xlsx` | 携程侧促销码表 |
| 同程 Q+E码表 | `code_tables/E_QE.xlsx` | 含两个 sheet：Q促销码表 / E促销码表 |

### 7.2 Q码表字段说明（携程）

| 字段名 | 用途 |
|--------|------|
| 促销名称 | 精确匹配键（标准化后比较）|
| 促销类型1级 | 商促 / 商券 / 平券 / 积分 / 平促 等 |
| 促销类型2级 | 子类：优享会 / 出行身份 / 门店新客 / 学生身份 等 |
| 十亿补贴 | 是否为基础促销（布尔值）|

### 7.3 竞品码表字段说明（携程）

| 字段名 | 用途 |
|--------|------|
| 促销&权益名称 | 精确匹配键（标准化后比较）|
| 促销类型1级 | 原始1级分类（含"身份类商促"等）|
| 促销类型1级-码表用 | 统一化后的1级，**优先使用**，为空时回退到促销类型1级 |
| 促销类型2级 | 子类 |
| 促销类型3级 | 更细子类 |

> **竞品侧身份类识别特别说明**：竞品侧身份类促销的「促销类型1级-码表用」有时为空，不能用此列识别身份类。必须用原始「促销类型1级」字段（取值 `身份类商促`），再通过 type2/type3 区分子类。

### 7.4 同程 Q码表字段说明

| 字段 | 用途 |
|------|------|
| 促销名称 | 精确匹配键 |
| 促销类型1级 | 商促 / 商券 / 平促 / 平券 / 积分 / 政府券 / 无促销 |
| 促销类型2级 | 子类 |
| 特殊类型 | 十亿补贴 |

### 7.5 同程 E码表字段说明

| 字段 | 用途 |
|------|------|
| 促销名称 | 精确匹配键 |
| 促销类型1级 | 商促 / 商券 / 平促 / 平券 / 积分 / 返现 / 未知（与Q侧类型名对齐）|
| 特殊类型 | 大额券/常规平台券 / 黑鲸优惠 |

## 八、同程特殊促销识别规则

以下类型需结合促销名称和金额动态判断（不能仅凭码表字段）：

| 特殊类型 | 识别规则 |
|---------|---------|
| 大额券 | E促销名称 = **`可用券`** 且该行促销金额 ≥ 50 |
| 黑鲸优惠 | E促销名称 = **`黑鲸优惠`**（与特殊类型字段双重确认）|

> `可用券` 在码表中特殊类型标注为 `大额券/常规平台券`：金额 ≥ 50 → 大额券（e_daejuan）；金额 < 50 → 普通平台券（e_pinjuan）。

## 九、促销数据文件 schema

**文件命名**：`原文件名_促销数据_YYYYmmdd_HHMM.xlsx`

**Sheet1：Q促销分行表**

| 列名 | 说明 |
|------|------|
| 平台 | 归因平台 |
| promo_code_set | 促销码表集合 |
| case编号 | 对应主数据 case_no |
| 工单号 | 对应主数据 order_no |
| 促销名称 | 促销原始名称 |
| 促销金额 | 促销金额（元）|
| 促销类型1级 | 码表匹配结果 |
| 促销类型2级 | 码表匹配结果 |
| 促销类型3级 | 码表匹配结果 |
| 特殊类型 | 黑鲸优惠 / 大额券 / 常规平台券 等 |
| 是否十亿补贴 | 是 / 否 |
| V1校验 | 该 case 的 V1 错误信息（Q侧）；通过则为空 |
| V2校验 | "未匹配"（该行促销未命中码表）；通过则为空 |
| 兜底方式 | 兜底1-LLM / 兜底2-Vision / 需人工介入；无兜底则为空 |
| 兜底优化建议 | 兜底处理输出的建议文字；无兜底则为空 |

**Sheet2：竞品促销分行表**

同 Q促销分行表，去掉「是否十亿补贴」列，V1校验列记录 竞品侧错误信息。

## 十、兜底处理机制（validate_fallback.py）

**触发条件**：`validate.py` 完成校验、写入 state.json 后，`case_audit` 非空（存在 V1 或 V2 错误的 case）。

**默认兜底：批量脚本化处理**

`validate_fallback.py` 默认从 state.json、原始 Excel、促销分行表一次性读取全部待处理 case：
- 按 Q侧 / 竞品侧独立处理，不跨侧写入优化建议或兜底结果
- 批量复用当前码表做 V2 校验，不再逐条调用 Agent 的 `check-v2`
- 用分行表促销金额重新做 V1 平衡校验
- 兼容「促销名称;金额」格式，例如 `普卡特权;87` 会拆分为名称 `普卡特权`、金额 `87`
- 对 V1/V2 全解决的 case，从 state.json 的 `case_audit` 移除，避免归因阶段继续标记人工校验
- 对 V2 已解析但未命中码表的 case，写入 `兜底1-V2待码表更新`，并从人工校验原因中移除，仅保留在促销分行表和 fallback stats 中
- 对原始促销明细为空、`#N/A` 或 `0` 的 case，写入 `需人工介入`

**可选兜底：LLM / Vision 模式**

如需重新启用 Claude API/Vision 解析，可显式传 `--llm`：
- 兜底2（Vision）：读取竞品截图 URL，识别价格优惠明细
- 兜底1（LLM）：重新解析原始促销文本
- 该模式需要 `ANTHROPIC_API_KEY`

**输出位置**

- 促销分行表（Q促销分行表 + 竞品促销分行表）：写入「兜底方式」「兜底优化建议」列
- state.json：写入 `agents.promo.fallback_summary`，供 Orchestrator 在完成报告中展示

**无 API Key 时的行为**：默认批量脚本化兜底仍会执行；只有显式传 `--llm` 时才需要 API Key。
